# GigaAM Docker

Синхронный HTTP-сервис распознавания русской речи на Go. CPU, ONNX Runtime 1.29.0, GigaAM v3 E2E RNNT или CTC, FP32 по умолчанию или готовые INT8-модели. Python в рабочем образе не нужен.

## Два варианта контейнера

Сервис можно собрать и запустить в одном из двух образов:

| Вариант | Сборка | ONNX Runtime | Когда выбирать |
|---|---|---|---|
| **Alpine Linux** | `Dockerfile.alpine`, `compose.yaml` + `compose.alpine.yaml` | Отдельно собирается под musl и сохраняется локально; штатный аллокатор mallocng | Основной выбор для экономии ОЗУ и места на диске |
| **Debian** | `Dockerfile`, `compose.yaml` | Скачивается готовая библиотека для glibc | Если важнее простая первичная сборка без компиляции ONNX |

API и настройки одинаковы. Это два варианта одного сервиса `asr`, одновременно запускать оба для работы не нужно. В конфигурации по умолчанию остаётся Debian: команда `docker compose up -d --build` без дополнительных файлов выбирает его. Для Alpine явно укажите оба Compose-файла, как ниже. Mimalloc в эти варианты не включён.

## Запуск

Все команды выполняются из корня репозитория. Один раз подготовьте `.env`:

```bash
# Существующий .env сохраняется.
test -f .env || cp .env.example .env
# Запишите в .env GIGAAM_API_KEY — например, результат openssl rand -hex 32.
```

Compose читает переменные из `.env` и передаёт сервису настройки, перечисленные в `compose.yaml`. Модели включаются в образ при сборке; отдельно скачивать их для Docker-запуска не нужно.

### Alpine Linux

```bash
# Один раз на каждой архитектуре: ONNX на всех потоках Docker-хоста.
sh scripts/prepare-onnx-alpine.sh > onnx-prepare.log 2>&1
# Сборка и запуск сервиса; ONNX больше не компилируется.
docker compose -f compose.yaml -f compose.alpine.yaml up -d --build
```

Просмотр логов:

```bash
docker compose -f compose.yaml -f compose.alpine.yaml logs -f asr
```

Остановка, когда сервис больше не нужен:

```bash
docker compose -f compose.yaml -f compose.alpine.yaml stop asr
```

Лог подготовки ONNX: `tail -f onnx-prepare.log` в другом терминале. Скрипт использует все потоки Docker-хоста; ограничить число задач можно через `ORT_BUILD_JOBS=6 sh scripts/prepare-onnx-alpine.sh`. Скрипт не читает `.env`. Это число процессов **сборки**; потоки инференса задаёт `GIGAAM_ONNX_THREADS` (по умолчанию 4).

Библиотека сохраняется в `.onnxruntime/amd64/` или `.onnxruntime/arm64/` и проверяется по SHA-256, версии и архитектуре при каждой сборке сервиса. Сохраните этот каталог: после очистки Docker-кэша пересобирать C++ не потребуется. Для изменения Go-кода, модели или FP32/INT8 достаточно обычной команды `docker compose -f compose.yaml -f compose.alpine.yaml up -d --build`. Первичная компиляция ONNX может быть долгой; [подготовка, перенос и обновление зависимостей](docs/alpine-build.md).

Все этапы этого Dockerfile основаны на Alpine. Исходники ONNX проверяются по SHA-512; итоговый образ содержит musl-библиотеку, Go-сервис, FFmpeg и модели. Компиляторы и Python остаются в сборочных этапах.

### Debian

```bash
docker compose -f compose.yaml up -d --build
```

Просмотр логов:

```bash
docker compose -f compose.yaml logs -f asr
```

Остановка, когда сервис больше не нужен:

```bash
docker compose -f compose.yaml stop asr
```

Этот вариант скачивает готовый ONNX Runtime 1.29.0 для нужной архитектуры, проверяет SHA-256 и запускает сервис в Debian с glibc.

Чтобы переключить существующий экземпляр, выполните команду `up -d --build` нужного варианта из той же директории. Compose пересоздаст сервис; переключайтесь после завершения текущей транскрибации. Для Alpine используйте оба `-f` и при последующих пересборках, чтобы сохранить выбранный вариант.

Проверка HTTP для обоих вариантов (при стандартном порте `8080`):

```bash
curl --fail http://localhost:8080/healthz
```

При сборке Docker скачивает выбранную GigaAM и Silero VAD (около 0,9 ГБ), проверяет размер и SHA-256 и включает файлы в образ. При запуске сервис использует готовые файлы, загружает графы и выполняет прогрев; сеть для моделей не нужна. HTTP запускается до инициализации. `healthz` сразу отвечает `200`, защищённые ручки до готовности возвращают `503 service_initializing`. Если файлов нет или ONNX не может их загрузить — `503 model_unavailable`. Готовность модели можно проверить авторизованным запросом `/v1/models` из примера ниже.

## Выбор FP32 / INT8

Задайте в `.env`:

```dotenv
GIGAAM_MODEL=gigaam-v3-e2e-rnnt
GIGAAM_PRECISION=int8
```

`GIGAAM_PRECISION` принимает `fp32` (по умолчанию) или `int8` для RNNT и CTC. Silero VAD всегда остаётся FP32. После изменения повторите команду сборки и запуска выбранного контейнера:

```bash
# Alpine
docker compose -f compose.yaml -f compose.alpine.yaml up -d --build
```

```bash
# Debian
docker compose -f compose.yaml up -d --build
```

Compose передаёт precision и на сборку, и при запуске. В образ скачивается **только выбранный комплект**. Смена FP32/INT8 обновляет слой моделей и настройку контейнера; Go-бинарник один для обоих вариантов, ONNX пересобирать не нужно. После первого обновления кода с поддержкой выбора последующие переключения не требуют перекомпиляции Go. При ручной сборке используйте `--build-arg GIGAAM_PRECISION=int8`.

Если оба комплекта уже скачаны в локальный `GIGAAM_MODEL_DIR` или смонтированный каталог контейнера, достаточно сменить `GIGAAM_PRECISION` и перезапустить процесс. Одной смены переменной недостаточно, если выбранных файлов нет: сервис вернёт `model_unavailable`, без автоматической подмены другим вариантом. Настройка применяется при старте, а не отдельно для каждого HTTP-запроса. В API имя модели прежнее, например `gigaam-v3-e2e-rnnt`; выбранный precision указан в логе `model ready`.

## Что показали тесты

Повторная серия от 10 сентября 2026 года после перезагрузки: Apple M4, 16 ГиБ ОЗУ, Docker Desktop / Linux ARM64; RNNT FP32, ONNX Runtime 1.29.0, 4 потока инференса. Входы — WAV и видео с аудио длительностью 462,016 с. Для каждого входа три пары запусков с чередованием порядка образов и полным прогревочным запросом перед измерением.

| Метрика | Alpine | Debian |
|---|---:|---:|
| Размер образа с моделями | 999 МиБ | 1359 МиБ |
| ОЗУ после загрузки, медиана | 895 МиБ | 1332 МиБ |
| ОЗУ после обработки, медиана | 1014 МиБ | 1452 МиБ |
| Максимальный наблюдавшийся пик ОЗУ | 1090 МиБ | 1553 МиБ |
| Инференс общего WAV, медиана | 27,31 с | 29,79 с |
| Инференс видео, медиана | 31,19 с | 30,27 с |

Alpine уменьшил размер образа примерно на **26,5%**, ОЗУ после загрузки — на **32,8%**. На WAV время инференса было меньше на 8,3%, на видео — больше на 3,1%; устойчивого общего преимущества по скорости эта серия не показала. Поэтому Alpine выбран прежде всего за экономию памяти и места. Все 24 транскрипции совпали.

Размер образа — сумма несжатых слоёв Docker без сборочного кэша, а не физический прирост `Docker.raw`. ОЗУ — `memory.current − inactive_file` контейнера, не всей Docker VM. Своп в этой серии не использовался, но macOS сжимала память. FFmpeg различался между образами; общий WAV служил контролем для инференса. Три пары на одном хосте дают ориентир, а не гарантию скорости на другом железе.

Полные условия и результаты: [повторные замеры Alpine / Debian](benchmarks/alpine-vs-debian-reboot-20260910-101540/report.md), [исходная серия](benchmarks/alpine-vs-debian/report.md). [Команды для повторения тестов](docs/container-benchmarks.md).

Отдельно проверен mimalloc поверх Alpine: время инференса сократилось на 3,4–3,6%, но ОЗУ после загрузки выросло примерно на 150 МиБ (17%). Для обычного запуска оставлен штатный mallocng. Экспериментальная сборка и подробности сохранены в [отчёте mimalloc](benchmarks/musl-vs-mimalloc/report.md).

Используются **готовые INT8-графы** из той же закреплённой ревизии моделей; самостоятельная квантизация не выполняется. На RNNT INT8 дал ускорение около 1,6× и уменьшил ОЗУ после загрузки с 895 до 263 МиБ. В тексте есть не только транслитерация терминов, но и изменения чисел; точность по ручному эталону не измерялась. FP32 остаётся по умолчанию. [Сборка и запуск INT8](experiments/int8/README.md), [результаты сравнения FP32 / INT8](benchmarks/fp32-vs-int8/report.md).

### Эксперимент с Intel GPU

На HP 260 G4 с Pentium Gold 6405U и Intel UHD Graphics 620 ускорить полный процесс транскрибации через GPU **не получилось**. Проверяли FP32 RNNT: рабочий Alpine с ONNX Runtime 1.29.0 на CPU и экспериментальный Debian с ONNX Runtime 1.24.1 + OpenVINO 2025.4.1, где на GPU выполнялся энкодер. CPU-сессии использовали два потока. Версии runtime и окружение различались: это сравнение двух вариантов сервиса.

| Аудио / запрос | CPU, весь HTTP-запрос | GPU, весь HTTP-запрос |
|---|---:|---:|
| 5 с, первый | 3,12 с | 29,08 с |
| 20 с, первый | 8,69 с | 60,64 с |
| 30 с, первый | 12,72 с | 61,70 с |
| 30 с, повтор | 12,66 с | 60,56 с |

Даже повторный запрос на 30-секундном аудио оказался примерно в **4,8 раза медленнее** на GPU. Тексты во всех четырёх парных запросах совпали побайтно. Пик памяти GPU-контейнера за запуск и запросы составил **5,24 ГиБ**, включая учитываемый cgroup файловый кеш.

Отдельный энкодер на 20-секундном входе после прогрева ускорялся, но это не дало выигрыша в полном сервисе. Возможная причина — затраты на обработку разных размеров входа; точный механизм не установлен. По результатам оставлен CPU, экспериментальная интеграция OpenVINO GPU удалена. Вывод относится к этой встроенной Intel GPU и проверенной конфигурации; NVIDIA и AMD не тестировались.

## Обращение к API

```bash
export GIGAAM_API_KEY='ваш-ключ'
curl --fail-with-body http://localhost:8080/v1/models \
  -H "Authorization: Bearer $GIGAAM_API_KEY"

curl --fail-with-body --max-time 5700 \
  http://localhost:8080/v1/audio/transcriptions \
  -H "Authorization: Bearer $GIGAAM_API_KEY" \
  -F 'file=@recording.mp3' \
  -F 'model=gigaam-v3-e2e-rnnt'
# {"text":"Распознанный текст."}

curl --fail-with-body --max-time 5700 \
  http://localhost:8080/v1/audio/transcriptions \
  -H "Authorization: Bearer $GIGAAM_API_KEY" \
  -F 'file=@recording.mp4' \
  -F 'model=gigaam-v3-e2e-rnnt' \
  -F 'response_format=text' -o transcript.txt
```

`file` и `model` обязательны. Допустимы `language=ru`, `response_format=json|text`, `stream=false`. Остальные поля, включая `prompt`, timestamps и `stream=true`, отклоняются с `400`. Совместимость ограничена этим подмножеством. Браузерный интерфейс, задания, история, БД и сохранение результатов не предусмотрены спецификацией.

Пример с Python-клиентом OpenAI (только на стороне клиента):

```python
import os
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8080/v1",
                api_key=os.environ["GIGAAM_API_KEY"], timeout=5700, max_retries=0)
with open("recording.wav", "rb") as audio:
    result = client.audio.transcriptions.create(
        model="gigaam-v3-e2e-rnnt", file=audio, response_format="json")
print(result.text)
```

## Обработка и данные

Поддерживаются WAV, MP3, FLAC, M4A/AAC, OGG/Opus, MP4 и WebM. FFprobe проверяет содержимое; FFmpeg выбирает первую аудиодорожку и преобразует её в mono PCM16 16 kHz. Плейлисты запрещены списком демультиплексоров, сетевые протоколы отключены. Нормализации громкости и шумоподавления нет.

Silero VAD читает по 512 отсчётов. Распознавание использует окна до 20 секунд (настройка ограничена 30 секундами), padding 300 мс и перекрытие 1 секунда при принудительной нарезке. Паузы сохраняются внутри фрагментов. Возле границы окна выбирается тихая точка. На пересечениях удаляется совпадающий суффикс/префикс только среди слов, относящихся ко времени перекрытия. Это эвристика; контроль качества длинных записей и стыков описан в [приёмке](docs/acceptance.md).

Исходник и подготовленный WAV находятся в отдельном каталоге `/work/request-*`. Аудиобуферы и признаки ограничены одним окном. Итоговый текст накапливается в памяти. Файлы закрываются и удаляются **до отправки HTTP 200**. При отмене текущий нативный ONNX-вызов завершается синхронно; слот и файлы удерживаются до его возврата. При сбое удаления ответ `500 cleanup_failed`, новые транскрибации получают `503 cleanup_pending`; очистка повторяется каждую секунду. Остатки после аварии удаляются на старте.

`/models` содержит готовые модели и их конфигурации, разложенные по ID, ревизии и FP32. Go-сервис проверяет наличие файлов, но не скачивает их и не вычисляет SHA-256 при старте. Проверка целостности выполняется при сборке образа. Compose не монтирует том поверх встроенных моделей. Перезапуск не восстанавливает прерванные запросы.

Логи содержат технические этапы, `request_id`, длительность, код ошибки. Имена пользовательских файлов, записи, текст и API-ключ в логи не попадают. Для транскрибаций выставляется `Cache-Control: no-store`.

### Метрики в логах

Логи Go-сервиса пишет `zerolog` v1.35.1 в stdout, по одному JSON-объекту на строку. Настройка находится в `internal/logging`: сохранены поля `time` (RFC3339Nano), `level` (`INFO`/`ERROR`), `msg` и все метрики. Производные логгеры запросов автоматически добавляют `request_id` и используют общий синхронизированный writer.

Каждый этап запроса пишет JSON-события `event=start` и `event=complete` с одним `request_id`. В конце появляется `stage=complete` с итоговыми метриками. Все времена — прошедшее реальное время, в миллисекундах с дробной частью:

| Поле итоговой записи | Что измеряется |
|---|---|
| `upload_ms`, `upload_bytes` | Приём multipart-запроса, запись исходника на диск и проверка полей; число байт самого файла |
| `probe_ms` | Проверка медиа через FFprobe |
| `convert_ms` | Извлечение звука и преобразование FFmpeg в WAV PCM16 mono 16 kHz |
| `inference_ms` | Весь проход распознавания: чтение WAV, VAD, признаки, ASR и сборка текста |
| `vad_ms` | Суммарное время определения речи Silero VAD |
| `frontend_ms` | Суммарное время вычисления признаков log-mel |
| `encoder_ms` | Суммарное время ONNX-энкодера |
| `decoder_ms` | RNNT-декодер и joint с выбором токенов; для CTC — выбор и свёртка токенов |
| `cleanup_ms` | Удаление временного каталога запроса |
| `duration_ms` | От начала обработчика до завершения очистки, до записи HTTP-ответа |
| `audio_seconds` | Длительность подготовленного аудио |
| `asr_chunks`, `asr_audio_seconds` | Число окон, переданных в ASR, и их суммарная длительность, включая padding и перекрытия |
| `rtf`, `inference_rtf` | Общее время / длительность аудио и время инференса / длительность аудио; `0.1` означает обработку в 10 раз быстрее реального времени |

`vad_ms`, `frontend_ms`, `encoder_ms`, `decoder_ms` входят в `inference_ms`; прибавлять их к нему не нужно. Неисполненные этапы отсутствуют; у неуспешных запросов нет RTF. На чистой тишине ASR может не вызываться. Этапы завершаются с `code=ok` либо кодом ошибки (внутренние этапы — `error`); итоговая запись содержит точный API-код. Логи не создаются для каждого кадра VAD или токена.

Сервис принимает файл от клиента: этот этап называется `upload`, скачивания пользовательского файла по URL нет. При запуске `stage=model_setup` показывает время проверки наличия файлов, `stage=model_load` — загрузку ONNX-графов и прогрев.

Для диагностики запуска поле `reason_code` указывает конкретную причину: `model_files_unavailable`, `runtime_load_failed`, `vocabulary_load_failed`, `asr_graph_load_failed`, `vad_load_failed`, `asr_warmup_failed` или `vad_warmup_failed`. Исходная ошибка сохраняется в цепочке Go-ошибок через `Unwrap`, а в JSON выводится только безопасный код без путей и содержимого нативных ошибок.

```bash
# Docker
docker compose logs -f asr

# Текущий локальный запуск: все этапы по мере выполнения
tail -f bin/server.log

# Только итоговые метрики запросов (если установлен jq)
tail -f bin/server.log | jq --unbuffered -c 'select(.stage == "complete")'
```

## Настройки и развёртывание

| `GIGAAM_MIN_SILENCE` / `GIGAAM_VAD_THRESHOLD` | `500ms` / `0.5` |
| `GIGAAM_ORT_LIBRARY` | `/usr/local/lib/libonnxruntime.so` |

Потоки ONNX задаются на сессию. Загружен один набор графов; запросы используют общие сессии, собственные тензоры и состояния RNNT/VAD. Увеличение параллелизма увеличивает память и конкуренцию за CPU. Очереди нет: занятые слоты дают `429 service_busy` и `Retry-After: 5` до чтения тела.

Лимита длительности записи нет. Сохраняются лимит размера исходника и таймаут обработки. Временный WAV использует RF64 при превышении 4 ГиБ.

Перед загрузкой проверяется место под максимальный исходник и резерв: 20,5 ГиБ при настройках по умолчанию. WAV дополнительно требует около 115,2 МБ на час записи. Перед конвертацией его допустимый размер рассчитывается по свободному месту за вычетом резерва; достижение этого размера возвращает `storage_unavailable`, обрезанный результат не распознаётся. Эта оценка не резервирует место от других процессов; ошибка заполнения диска также обрабатывается. `/work` — дисковый слой контейнера, не tmpfs. Для отдельного диска выделите каталог только этому экземпляру и предоставьте UID/GID `10001:10001` доступ на запись. Нельзя делить `/work` между экземплярами или размещать его внутри кэша моделей.

Для смены модели запишите `GIGAAM_MODEL=gigaam-v3-e2e-ctc` в `.env` и повторите команду `up -d --build` выбранного варианта из раздела «Запуск» (для Alpine — с обоими Compose-файлами). Compose передаёт модель и в сборку, и в окружение контейнера. При ручной сборке добавьте `--build-arg GIGAAM_MODEL=gigaam-v3-e2e-ctc` и используйте `-f Dockerfile.alpine` для Alpine или `-f Dockerfile` для Debian; выбранная модель станет значением по умолчанию в образе. HTTP-поле `model` должно соответствовать установленной модели.

Compose по умолчанию публикует порт только на localhost. Для настроенного HP доступ по домашнему IP описан в [отдельной инструкции](docs/hp-lan.md). Для доступа извне измените binding и используйте TLS reverse proxy. Для Docker secrets удалите `GIGAAM_API_KEY` из environment Compose, подключите secret и задайте `GIGAAM_API_KEY_FILE=/run/secrets/gigaam_api_key`.

Docker healthcheck использует `GIGAAM_PORT`. `GIGAAM_HEALTH_START_PERIOD` меняет start period; остальные параметры можно переопределить стандартным Compose override. `unhealthy` сам по себе не перезапускает контейнер. Health не зависит от диска, готовности модели, занятости и очистки.

## Таймауты и остановка

Go ограничивает заголовки 15 секундами, загрузку тела — отдельным read deadline, обработку — context timeout, передачу готового ответа — write deadline. Общий `http.Server.WriteTimeout` намеренно не установлен, иначе длительное распознавание оборвётся до формирования результата.

Клиент и прокси должны ждать не менее суммы трёх фаз: по умолчанию 30 + 60 + 5 = 95 минут, желательно с запасом. Во время ASR ответ не передаётся. [Пример nginx](docs/nginx.conf) отключает буферизацию запроса/ответа и кэш. При собственной буферизации прокси обеспечьте удаление его временных файлов. Ошибка соединения после вычисления результата не позволяет получить его повторно; клиент заново загружает файл.

SIGTERM закрывает допуск новых транскрибаций, оставляя health доступным, и даёт `GIGAAM_GRACE_PERIOD` активным запросам. После grace отменяются операции, включая FFmpeg и чтение тела. Текущий ONNX-вызов завершается до очистки. Docker `GIGAAM_STOP_GRACE_PERIOD` должен покрывать этот период, длительность одного нативного вызова и завершение отправки ответа; пример — 7 минут. Фактическая задержка нативной отмены требует замера на целевом CPU.

## Разработка и проверки

Нужны Go 1.26.1, C-компилятор, FFmpeg/FFprobe. Для запуска инференса нужна ONNX Runtime 1.29.0; для обычных тестов она не нужна. Фактически загруженная версия выводится в логе `ONNX Runtime initialized` в поле `version`.

**Перед локальным запуском выбранная модель GigaAM и Silero VAD должны быть скачаны заранее.** Укажите каталог с готовыми файлами в `GIGAAM_MODEL_DIR`, а вариант модели — в `GIGAAM_PRECISION` (`fp32` по умолчанию). Приложение самостоятельно модели не скачивает; при отсутствии файлов API распознавания возвращает `503 model_unavailable`. При сборке Docker-образа модели скачиваются автоматически.

```bash
make test
make vet
make build
# Для локального запуска нужны заранее скачанные модели, ключ, рабочий каталог и runtime:
GIGAAM_API_KEY=local-key GIGAAM_MODEL_DIR="$PWD/models" \
GIGAAM_WORK_DIR="$PWD/work" GIGAAM_ORT_LIBRARY=/path/to/libonnxruntime.so \
  ./bin/gigaam
```

Тесты проверяют ошибки API, очистку до ответа, отмену, занятость, таймауты, health, форматы аудио, наличие установленных моделей и гонки. Сравнение настоящих моделей с официальным декодированием выполняется отдельно: [релизные комплекты](docs/models.md), [приёмка и ограничения проверки](docs/acceptance.md).

В `internal/api` маршруты и авторизация отделены от обработки транскрибации, multipart-загрузки, очистки хранилища и завершения работы. Инициализация модели находится в `cmd/gigaam/initialize.go`; конфигурация, значения по умолчанию и чтение переменных окружения — в `internal/config`. Метрики в `internal/metrics` используют типизированные этапы и числовые поля; JSON-имена и правила пропуска отсутствующих значений сохранены.

Для локального запуска на Linux файлы можно заранее подготовить командой `sh scripts/download-models.sh internal/models/manifest.json /path/to/models gigaam-v3-e2e-rnnt fp32` (для INT8 замените последний аргумент на `int8`; нужны `curl`, `jq`, `sha256sum`). Также можно использовать существующий каталог моделей с той же структурой.
