# Alpine на HP 260 G4: сборка и запуск

10 сентября 2026 года. Debian заменён работающим Alpine-контейнером. На мини-ПК подтверждены Alpine 3.24.1 и musl x86-64; готовность модели и два запроса распознавания прошли. Контейнер оставлен работать с политикой `unless-stopped`. При первоначальном запуске порт был только `127.0.0.1:8080`; позже добавлен [доступ по LAN](../../docs/hp-lan.md) на `192.168.0.36:8080` с сохранением loopback.

Позже на HP включён лимит 20 ГиБ после очистки тестовых образов и кэша. Четыре потока ONNX проверены и затем возвращены два; [текущие настройки](../../docs/hp-lan.md). Числа ниже относятся к исходным замерам на двух потоках.

Рецепт последующих сборок обновлён: ONNX хранится локально, отдельно от Docker-кэша. См. [инструкцию](../../docs/alpine-build.md). Ниже — история первоначальной сборки и замеров.

## Сборка

Pentium Gold 6405U, два физических ядра / четыре логических потока, Ubuntu 24.04.2, 8 ГБ ОЗУ. ONNX Runtime 1.29.0 собран из исходников под musl на **всех четырёх потоках**. Модель прежняя: FP32 RNNT; инференс использует два потока и один запрос одновременно. Лимит загрузки на мини-ПК по-прежнему 1 ГиБ.

Первый проход остановился почти в конце: GCC 15.2.0 сообщил `maybe-uninitialized` в своём `bits/unicode.h`, включённом через `chrono` / `format` из `logging.cc` ONNX. Из-за `-Werror` предупреждение стало ошибкой. Признаков OOM в этом сбое нет; на хосте оставался запас памяти.

В исходный `Dockerfile.alpine` добавлено точечное правило CMake (теперь оно находится в `Dockerfile.onnx-alpine`): только для `logging.cc` и только при GCC 15 применяется `-Wno-error=maybe-uninitialized`. Предупреждение остаётся видимым; остальные предупреждения и уровень оптимизации не изменены. После исправления кэш сохранил скомпилированные объекты: повторный C++ этап потребовал только 33 шага и завершился примерно за три минуты. Общее время, включая первую попытку, диагностику, упаковку и тесты, — около 70 минут.

Debian продолжал работать во время сборки. Переключение выполнено после успешной сборки образа; два тестовых запроса завершились успешно. Предыдущий Debian-образ сохранён как `gigaam-service:debian-hp-backup`.

## Проверка

Тот же 30-секундный WAV, что при [первом запуске Debian](../hp-6405u-first-run/report.md). Один запрос после запуска, затем повторный. Все четыре текста (два Debian и два Alpine) совпали побайтно; контрольные суммы и метрики в [results.json](results.json).

| Показатель | Alpine |
|---|---:|
| Первый запрос целиком | 12,65 с |
| Повторный запрос целиком | 12,59 с |
| ОЗУ сразу после готовности модели | 886,7 МиБ |
| ОЗУ после запросов и ожидания | 973,9 МиБ |
| CPU в простое после ожидания, разовый замер | 0,02% |
| Размер образа по Docker Image Inspect | 1 690 803 254 байта, около 1,57 ГиБ |
| Свободное место на корневом разделе | около 12,4 ГиБ |

Для сравнения, на Debian те же короткие запросы заняли 12,57 и 12,46 с, а ОЗУ после ожидания — 1,421 ГиБ. В этой проверке скорость практически одинаковая, Alpine расходует меньше памяти. Это проверка запуска сразу после продолжительной компиляции, а не контролируемый повторный бенчмарк. Температура CPU не фиксировалась, на хосте после компиляции осталось около 672 МиБ swap; другие приложения не закрывались.

Docker учитывает общие данные слоёв и кэша: после сборки оба образа вместе показаны как 3,403 ГБ, build cache — 8,962 ГБ (5,018 ГБ reclaimable). Эти числа нельзя просто складывать для оценки физического места. Старый образ и кэш автоматически не удалялись. `/work` пуст после завершения запросов.

## Где смотреть логи

На мини-ПК полный лог обеих попыток сборки, переключения и проверки:

```bash
tail -f ~/gigaam-service/alpine-build.log
```

В конце успешной попытки записано `exit=0`. Предыдущая ошибка сохранена выше для диагностики.

С Mac:

```bash
ssh dmitry@192.168.0.36 'tail -f ~/gigaam-service/alpine-build.log'
```

Логи работающего сервиса на мини-ПК:

```bash
cd ~/gigaam-service
sudo docker compose logs -f asr
```

В `.env` мини-ПК сохранён `COMPOSE_FILE=compose.yaml:compose.alpine.yaml:compose.local.yaml`, поэтому обычные команды `docker compose` выбирают Alpine. Подготовленная ONNX-библиотека находится в `.onnxruntime/amd64/`; `ORT_BUILD_JOBS` при обычной сборке сервиса больше не используется. Для повторной сборки из этой папки:

```bash
sudo docker compose up -d --build
```

Явный эквивалент с указанием Compose-файлов:

```bash
sudo docker compose -f compose.yaml -f compose.alpine.yaml -f compose.local.yaml up -d --build
```

Доступ с Mac через существующий временный SSH-туннель — `http://127.0.0.1:18082`; `/healthz` и авторизованный `/v1/models` после переключения вернули HTTP 200. Ключ остался прежним, в `.env` мини-ПК. Восстановление туннеля и пример отправки файла описаны в [инструкции первого запуска](../hp-6405u-first-run/report.md#использование).
