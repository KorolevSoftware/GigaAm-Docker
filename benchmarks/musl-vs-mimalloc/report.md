# Alpine: mallocng и mimalloc

10 сентября 2026 года. Сравнение одного и того же Alpine-сервиса с системным аллокатором musl 1.2.6 и mimalloc 3.5.1.

В этой серии mimalloc сократил медианное время инференса на **3,4% для WAV** и **3,6% для видео**, но потребовал **на 150 МиБ (16,8%) больше ОЗУ после загрузки**. Пик ОЗУ вырос на 96 МиБ (8,8%), размер образа — на 0,76 МиБ. При приоритете экономии памяти разумно оставить mallocng; небольшое ускорение mimalloc пока подтверждено только этой серией.

## Что изменилось

- Mimalloc собран из закреплённого архива v3.5.1 под musl, Release, `MI_LIBC_MUSL=ON`, `MI_OVERRIDE=ON`; остальные параметры по умолчанию. В частности, mimalloc 3.5.1 включает режим THP FULL; это часть тестируемой конфигурации. В Linux VM THP настроен как `[always] madvise never`.
- Сборка и CTest выполнялись с параллелизмом 6. Все 6 тестов аллокатора прошли. ONNX повторно не компилировался.
- К готовому Alpine-образу добавлены библиотека, лицензия и `LD_PRELOAD=/usr/local/lib/libmimalloc.so`. Переменная наследуется дочерним FFmpeg. Go использует собственный аллокатор для Go-кучи.
- SHA-256 Go-бинарника, ONNX и FFmpeg совпадают между образами; модели и исходные слои наследуются от того же образа. Проверки сохранены в `build-checks.json`. Отладочная статистика mimalloc проверена отдельным запуском curl; в тестах диагностика отключена. Загрузка библиотеки в процесс сервиса подтверждена `/proc/1/maps` во всех 6 запусках.

## Протокол

- Apple M4, 16 ГиБ RAM; Docker Desktop, Linux ARM64, 10 vCPU и 7,75 ГиБ RAM VM. Docker хранится на внешнем Goida.
- RNNT FP32, ONNX Runtime 1.29.0, четыре потока инференса; шесть задач сборки не меняют число потоков инференса.
- Общий WAV PCM16 mono 16 кГц и исходное MP4 с аудио 462,016 с. В обоих образах один и тот же FFmpeg 8.1.2.
- Три пары на каждый вход. Порядок WAV: mallocng/mimalloc, mimalloc/mallocng, mallocng/mimalloc; видео — обратный.
- Каждый контейнер: готовность модели, 12 с простоя, полный первый запрос для прогрева, 2 с паузы, измеряемый запрос, 2 с паузы и 12 с простоя. Всего 12 контейнеров, 24 запроса. Первый запрос исключён из медиан скорости, но входит в наблюдаемый пик ОЗУ.
- Одновременно обрабатывал аудио один тестовый контейнер. Кроме измерительных docker exec, один короткий вспомогательный контейнер проверил размер библиотеки и THP во время первой видеосессии; сборок не было. Основной сервис остановлен на время серии и восстановлен после неё.

| Максимальный RSS | 1033.3 МиБ | 1194.8 МиБ |
| Записываемый слой после очистки | 0 байт | 0 байт |
| CPU контейнера в простое с мониторингом, медиана | 2.02% | 2.19% |
| CPU при измеряемом запросе, медиана | 377.4% | 374.7% |

ОЗУ — cgroup `memory.current − inactive_file`, RSS — `/proc/1/status`. Выборки каждые 0,5 с плюс время docker exec: короткие пики могут быть пропущены. CPU по дельте cgroup cpu.stat: 100% равно одному ядру; включает затраты самого сборщика метрик через docker exec. Значение CPU в простое поэтому не равно потреблению сервиса без мониторинга. Размер образа — несжатые слои Docker, без build cache. Слои образов общие, поэтому их размеры нельзя складывать как физический расход диска. Во время запроса дополнительно нужно место для входа и WAV.

## Память хоста и ограничения

- Первую попытку после сборки прервали из-за повышенного давления памяти и обращений к свопу. Она сохранена в `aborted-memory-pressure` и исключена из всех таблиц. Перед основной серией Docker Desktop перезапущен.
- Своп macOS на старте: 505.50 МиБ; максимум: 505.50 МиБ. Прирост счётчиков swapins/swapouts: 1320/0 страниц.
- Наблюдаемые уровни давления памяти: [1] (1 — нормальный, 2 — повышенный). Компрессор macOS: 2.28–5.90 ГиБ.
- Максимальные счётчики Linux VM pswpin/pswpout: 0/0 страниц.
- Своп и давление памяти записывались примерно каждые 5 с; данные для измеряемых запросов выделены в `summary.json`. Это не помиллисекундная проверка отсутствия свопа. Другие приложения macOS не закрывались, температура и частоты CPU не фиксировались.
- Три пары на одном хосте — ориентир для этой нагрузки; небольшие различия не доказывают устойчивое ускорение на других входах или серверах.

## Проверка результата и воспроизведение

- Все 24 запроса успешны, каждый дал 42 ASR-фрагмента. Уникальных SHA-256 текста: 1; он совпал с результатом предыдущего сравнения Debian/Alpine.
- Основной сервис восстановлен: контейнер healthy, `/healthz` и авторизованный `/v1/models` ответили HTTP 200. Экспериментальный mimalloc не включён по умолчанию.
- `Dockerfile.alpine.mimalloc` содержит сборку и тесты аллокатора; команды сборки и сравнения — в README.
- Полные параметры, ID образов, хэши входов и порядок запусков: `measurements/environment.json`. Метрики по контейнерам: `measurements/*/results.json`; сводка: `summary.json`.
- Сырые логи, тексты транскрибации и частые выборки памяти сохранены локально и исключены из Git.

Источники: [mimalloc 3.5.1](https://github.com/microsoft/mimalloc/tree/v3.5.1), [замена аллокатора ONNX Runtime](https://onnxruntime.ai/docs/performance/tune-performance/memory.html).
