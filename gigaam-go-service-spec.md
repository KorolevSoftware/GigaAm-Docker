# Техническое задание: синхронный сервис транскрибации GigaAM на Go

Версия: 1.4. Дата: 09.09.2026.

## 1. Назначение

Разработать сервис на Go для локального распознавания русской речи из аудио и видео. Развёртывание — Docker на Linux, вычисления — CPU через ONNX Runtime. Модель выбирается переменной окружения `GIGAAM_MODEL`; по умолчанию — GigaAM v3-e2e-rnnt в FP32. Модели автоматически скачиваются при первом запуске контейнера.

Единственный режим транскрибации — синхронный: клиент отправляет файл, HTTP-соединение остаётся открытым до завершения обработки, результат возвращается в теле того же ответа. Это относится и к часовым записям. Нарезку аудио сервис выполняет автоматически.

Исходник и подготовленное аудио существуют только как временные файлы на время запроса. После обработки их немедленно удаляют. Готовый текст возвращают клиенту и не сохраняют на сервере.

В первую версию не входят: асинхронные задания, постоянная очередь, БД, история запросов, хранение результатов, ручки статуса и скачивания, нормализация громкости, шумоподавление, диаризация, LLM-коррекция, перевод, WebSocket, загрузка по внешнему URL, S3/MinIO. Пунктуация самой e2e-модели сохраняется.

## 2. Архитектура и жизненный цикл запроса

```text
POST /v1/audio/transcriptions
    → авторизация и получение свободного слота
    → загрузка исходника во временный каталог
    → FFprobe / FFmpeg
    → WAV, mono, 16 kHz, PCM16
    → Silero VAD и автоматическая нарезка
    → признаки и выбранная GigaAM через ONNX Runtime
    → объединение текста в памяти
    → закрытие файлов и удаление каталога запроса
    → HTTP 200 с JSON или обычным текстом
```

Сервис работает одним процессом в контейнере. Модели скачиваются в отдельный постоянный Docker volume `/models`; после скачивания используются повторно. Аудио и текст в этот volume не записываются. Основные модули Go: HTTP API, ограничитель параллелизма, временные файлы, FFmpeg, VAD, ASR и формирование ответа.

Каждый запрос имеет собственный context, случайный `request_id` и отдельный рабочий каталог. `request_id` нужен для диагностики и заголовка `X-Request-ID`; получить результат позднее по нему нельзя.

## 3. Модель и вычисления

- Основная конфигурация: `GIGAAM_MODEL=gigaam-v3-e2e-rnnt`, ONNX FP32, CPU. Также поддержать `gigaam-v3-e2e-ctc` в FP32. Одновременно загружается одна выбранная модель; смена переменной требует пересоздания контейнера.
- Использовать Go-обвязку нативного ONNX Runtime, например `yalue/onnxruntime_go`.
- Комплект модели содержит необходимые ONNX-графы, словарь/токенизатор, конфигурацию подготовки признаков и Silero VAD.
- Подготовку признаков, соответствующее модели CTC/RNNT-декодирование и преобразование токенов сверить с официальной реализацией GigaAM. Один вызов ONNX сам по себе не заменяет весь этот конвейер.
- Готовые совместимые ONNX-комплекты скачиваются автоматически. Если требуется собственный экспорт, его выполняет разработчик при подготовке релиза, публикует комплект и фиксирует его в манифесте загрузчика. Пользователю не нужно экспортировать модель вручную. Python допустим при подготовке релиза и сравнении результатов, но не требуется в рабочем контейнере.
- Зафиксировать совместимые версии Go-библиотеки, ONNX Runtime, экспортёра и ревизию модели. Проверять контрольные суммы файлов моделей.
- HTTP-сервер запускать до скачивания и длительной инициализации модели, чтобы `/healthz` сразу отвечал. Проверить кэш, скачать недостающие файлы, загрузить модель и VAD, выполнить прогрев и стартовую очистку. До завершения инициализации ручка транскрибации возвращает `503 service_initializing`; health check от неё не зависит.
- Модели не загружаются заново на каждый запрос. Сессии переиспользуются; изменяемое состояние декодера изолировано между запросами.
- По умолчанию обрабатывать один запрос одновременно. Потоки ONNX Runtime настраиваются отдельно. Рост параллелизма не должен создавать неограниченное число сессий и потоков.
- INT8 может быть добавлен позднее отдельным комплектом весов с проверкой качества. Переключение точности не входит в первую версию.


### 3.1. Выбор модели

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `GIGAAM_MODEL` | `gigaam-v3-e2e-rnnt` | Выбор поддерживаемой ASR-модели |
| `GIGAAM_MODEL_DIR` | `/models` | Постоянный кэш ASR и VAD |
| `GIGAAM_AUTO_DOWNLOAD` | `true` | Автоматическое скачивание недостающего комплекта |

В первой версии поддерживаются только `gigaam-v3-e2e-rnnt` и `gigaam-v3-e2e-ctc`, обе в FP32. Это разные декодеры, а не варианты квантизации. Для каждой модели нужны собственные проверенные графы, конфигурация признаков и токенизатор. Неизвестное значение переменной отклонять при проверке конфигурации с перечислением допустимых значений.

Поле `model` HTTP-запроса должно совпадать с выбранной серверной моделью. Оно не запускает скачивание другой модели и не переключает глобальное состояние. Смена модели — изменение environment в Compose и пересоздание контейнера. Одновременное обслуживание нескольких моделей не требуется.

### 3.2. Автоматическое скачивание и кэш

1. При первом запуске контейнер сам скачивает выбранную ASR-модель, необходимые конфигурации/словари и Silero VAD. Скачивание выполняет Go-сервис при старте, а не `docker build`, чтобы модель можно было менять через environment без пересборки образа.
2. В состав релиза включить манифест поддерживаемых моделей: ID, архитектура, точность, фиксированная ревизия, список файлов, HTTPS-адреса, размеры и SHA-256. Использовать проверенные готовые экспорты либо опубликованные разработчиком комплекты. Подмена PyTorch-весов вместо ONNX не допускается. Конкретные источники комплектов проверяются и фиксируются при реализации.
3. Скачивать только отсутствующие или повреждённые файлы выбранной ревизии. Проверять контрольные суммы до загрузки в ONNX Runtime. Не получать автоматически новую ревизию из `latest`/`main`.
4. Загружать потоком во временные `.part`-файлы в кэше. После проверки атомарно переименовывать; частичный комплект не считать готовым. Один загрузчик на экземпляр, до трёх попыток на файл с паузой и ограничением времени. Ограничения скачивания настраиваются.
5. Кэш разделять по модели, ревизии и точности, например `/models/<model>/<revision>/fp32/`. VAD хранить отдельным версионированным комплектом. Разные модели не перезаписывают файлы друг друга.
6. При повторном запуске с полным корректным кэшем не обращаться к сети. Кэш сохраняется после пересоздания контейнера и не очищается вместе с записями пользователей. Удаление старых моделей — отдельное действие оператора, автоматического удаления в первой версии нет.
7. Пока идёт скачивание или прогрев, `/healthz` отвечает `200`, а транскрибация — `503 service_initializing`. В логах отражать выбранную модель, этап и прогресс скачивания без секретов.
8. После исчерпания попыток при сетевой ошибке, нехватке диска или нарушении контрольной суммы транскрибация возвращает `503 model_unavailable`. Живой процесс продолжает отвечать на `/healthz`; не использовать другую модель молча. Для повторной инициализации после исправления причины перезапустить контейнер.
9. `GIGAAM_AUTO_DOWNLOAD=false` запрещает сетевые загрузки. При полном кэше сервис работает офлайн; при неполном — `503 model_unavailable` и понятная ошибка в журнале.
10. В скачивании участвуют только веса и конфигурации. Исходные записи и текст не передаются источнику моделей. Рабочий процесс имеет права записи в кэш; ASR не изменяет проверенные файлы весов.

## 4. Входные файлы и FFmpeg

Основной формат — WAV. Также поддержать MP3, FLAC, M4A/AAC, OGG/Opus, MP4 и WebM при наличии соответствующих декодеров в поставляемом FFmpeg.

Принимать файл через `multipart/form-data`, поле `file`. Проверять содержимое FFprobe, не доверяя расширению и MIME-типу. Для видео и многодорожечного файла брать первую аудиодорожку. Отсутствие аудиодорожки — ошибка запроса.

В Docker-образ включить FFmpeg и FFprobe. Базовая команда преобразования:

```bash
ffmpeg -nostdin -y -i input.mp3 \
  -map 0:a:0 -vn -ac 1 -ar 16000 -c:a pcm_s16le prepared.wav
```

Выход: WAV, один канал, 16 000 Hz, signed PCM 16 bit. Стерео сводится в моно. Нормализация громкости, компрессия и шумоподавление не применяются.

Запускать FFprobe и FFmpeg через `exec.CommandContext` без shell. Использовать серверные пути и ограниченный по размеру stderr. Не поддерживать плейлисты со ссылками на другие файлы или сетевые ресурсы; разрешённые протоколы ограничить локальными файлами/pipe внутри рабочего каталога.

Загрузку писать потоком на диск, без размещения всего файла в RAM. Во время записи проверять лимит размера. FFmpeg пишет во временный WAV; после успеха проверить параметры и длительность. Подготовленный пользователем WAV также проверяется; если параметры подходят, его можно использовать напрямую без дополнительного перекодирования.

## 5. Длинные записи

- Silero VAD определяет речевые участки. Слишком длинную непрерывную речь делить на ограниченные окна с перекрытием.
- Максимальную длину фрагмента выбрать по ограничениям конкретного экспорта GigaAM и подтвердить интеграционными тестами. Padding и overlap настраиваются.
- Читать и обрабатывать аудиофрагменты последовательно с ограниченным буфером. Не держать часовой WAV и все его признаки в RAM.
- Не склеивать речевые фрагменты в единое аудио с удалением пауз. Контекст на границах сохранять padding/перекрытием.
- Проверить отсутствие систематических повторов текста и потерь слов на стыках. Объединять текст в исходном порядке.
- В памяти накапливать только необходимое состояние обработки и итоговый текст. Размер текста ограничен максимально допустимой продолжительностью записи.
- Отсутствие речи — успешный ответ с пустым текстом.
- Частичный текст при ошибке или отмене не выдавать как успешный результат.

## 6. Временные файлы и немедленное удаление

Рабочий каталог — `/work`, предназначенный только для временных файлов сервиса:

```text
/work/
  request-<random-id>/
    source.bin          # исходные байты загрузки
    prepared.wav        # подготовленное аудио, если необходимо
    ...                 # временные файлы конвертации/обработки
```

Каталог запроса создавать через `os.MkdirTemp`, с доступом только пользователю процесса. Имена клиента не использовать для построения путей. Пользовательские файлы не помещать в каталог моделей.

### Правила очистки

1. Сразу после создания каталога зарегистрировать обязательную очистку на всех путях выхода из обработчика.
2. При успехе собрать полный текст в памяти, закрыть все файловые дескрипторы, дождаться завершения процессов и удалить каталог запроса **до отправки успешного ответа**.
3. При ошибке загрузки, конвертации, распознавания, таймауте или отключении клиента остановить обработку и удалить все файлы запроса сразу после остановки использующих их операций.
4. При отмене нативного вызова ONNX освобождать слот и связанные ресурсы только после фактического завершения вызова. Пока он завершается, не запускать следующий этап.
5. Не записывать `result.json` или `transcript.txt` на серверный диск. Текст и сериализованный ответ существуют только в памяти до завершения запроса, затем ссылки на них освобождаются.
6. Не хранить исходники, WAV или текст в логах, диагностических дампах приложения и кэше результатов. Для `/v1/audio/transcriptions` возвращать `Cache-Control: no-store`.
7. Если удаление не удалось, вернуть `500 cleanup_failed` вместо успешного ответа, записать служебную ошибку без пользовательского содержимого и повторять удаление. `/healthz` продолжает отвечать `200`; ручка транскрибации возвращает `503 cleanup_pending`. Новые запросы не принимать до восстановления очистки.
8. При аварийном завершении процесса немедленная очистка невозможна. При следующем старте, **до допуска транскрибаций**, удалить оставшиеся каталоги запросов в выделенном `/work`. Не восстанавливать прерванное распознавание.

Отложенного хранения по TTL нет. `/work` не требует постоянного Docker volume; по умолчанию используется дисковая файловая система контейнера. Если оператор подключает отдельный временный диск, он выделяется только этому экземпляру сервиса и очищается по тем же правилам. Tmpfs не является значением по умолчанию: длинные записи не должны целиком занимать RAM.

Удаление означает удаление файлов из файловой системы; гарантированное физическое стирание блоков носителя не входит в ТЗ.

## 7. OpenAI-совместимый API и результат

### `POST /v1/audio/transcriptions`

Поддержать явно документированное подмножество API транскрибации OpenAI:

| Поле | Поведение |
|---|---|
| `file` | Обязательный аудио- или видеофайл |
| `model` | Обязательный ID, совпадающий с `GIGAAM_MODEL`; по умолчанию `gigaam-v3-e2e-rnnt` |
| `language` | Необязательно; отсутствует или `ru` |
| `response_format` | `json` по умолчанию или `text` |
| `stream` | Отсутствует или `false` |

Неизвестную модель, неподдерживаемый язык и неподдерживаемые возможности (`prompt`, `stream=true`, `verbose_json`, word timestamps и др.) отклонять с `400` и понятным кодом. Не имитировать поддержку молчаливым игнорированием параметров.

Пример запроса:

```bash
curl http://localhost:8080/v1/audio/transcriptions \
  -H "Authorization: Bearer YOUR_SERVICE_KEY" \
  -F "file=@recording.mp3" \
  -F "model=gigaam-v3-e2e-rnnt" \
  -F "response_format=json"
```

Успех — `200 OK`, `Content-Type: application/json`:

```json
{"text":"Распознанный текст записи."}
```

При `response_format=text` вернуть UTF-8 текст с `Content-Type: text/plain; charset=utf-8`. Клиент может сразу сохранить его у себя:

```bash
curl --fail-with-body http://localhost:8080/v1/audio/transcriptions \
  -H "Authorization: Bearer YOUR_SERVICE_KEY" \
  -F "file=@recording.mp3" \
  -F "model=gigaam-v3-e2e-rnnt" \
  -F "response_format=text" \
  -o transcript.txt
```

Результат существует только в этом HTTP-ответе. Нет `job_id`, ответа `202`, ссылок на скачивание или последующего получения статуса. Для повторного распознавания файл загружается заново. При обрыве соединения во время передачи готового результата восстановить его на сервере нельзя; успешная запись в сокет не гарантирует получение клиентом.

Не отправлять `200` или часть тела до полного успеха обработки и очистки. Совместимость распространяется на описанные поля и ответы; весь OpenAI API не реализуется. Обращения к OpenAI и OpenAI API-ключ не требуются.

### `GET /v1/models`

После инициализации вернуть OpenAI-совместимый список из одной выбранной модели с ID из `GIGAAM_MODEL` и `owned_by: local`. До готовности модели вернуть `503 service_initializing`, при ошибке её инициализации — `503 model_unavailable`. Клиент должен выполнять поддерживаемый сценарий при замене `base_url`, ключа и имени модели.

## 8. Параллелизм, таймауты и сбои

Настройки по умолчанию:

| Параметр | Значение |
|---|---|
| Максимальный файл | 1 GiB |
| Максимальная длительность записи | 4 часа |
| Одновременные запросы транскрибации | 1 |
| Приём тела запроса | До 30 минут |
| Обработка после загрузки: FFprobe, FFmpeg, VAD, ASR | До 60 минут суммарно |
| Передача готового ответа | До 5 минут |

Слот занимается до чтения файла и удерживается до завершения обработки/освобождения ресурсов. Если все слоты заняты, вернуть `429 service_busy` с `Retry-After`, не сохраняя файл. Очереди ожидания в приложении нет.

Все лимиты настраиваются. Максимальную длительность проверять до ASR, а при недостоверных метаданных также ограничивать фактически декодированное аудио. Перед загрузкой и конвертацией проверять свободное место с учётом WAV и резерва. При нехватке — `503 storage_unavailable`.

При превышении таймаута обработки отменить context, остановить FFmpeg и дальнейшие вызовы модели, выполнить очистку и вернуть `504 transcription_timeout`, если соединение ещё открыто. При неподдерживаемой немедленной отмене ONNX дождаться текущего ограниченного вызова; задержка освобождения ресурсов должна быть измерена и документирована.

Отключение клиента отменяет запрос. После рестарта сервиса запрос не возобновляется, клиенту требуется повторная загрузка. Автоматических повторных распознаваний и идемпотентного кэша нет.

При SIGTERM отключить приём новых транскрибаций, дать активным запросам настраиваемое время завершиться. Пока HTTP-сервер доступен, `/healthz` продолжает отвечать `200`. По истечении grace period отменить операции и выполнить очистку. При принудительном завершении остатки очищаются на следующем старте.

В README описать согласование Go server deadlines, таймаутов клиента, ingress и reverse proxy с указанными фазами. Прокси должен допускать отсутствие данных в ответе во время распознавания. Загрузка через прокси по возможности передаётся без буферизации на его диск; если буферизация нужна, его временные файлы также должны удаляться по завершении запроса.

## 9. Ошибки, авторизация и диагностика

Статический Bearer API-ключ из файла секрета или переменной окружения. Обе ручки `/v1/*` защищены. История пользователей и управление владельцами файлов не требуются.

Ошибки возвращаются единообразно:

```json
{
  "error": {
    "message": "Размер файла превышает допустимый лимит.",
    "type": "invalid_request_error",
    "param": "file",
    "code": "file_too_large"
  }
}
```

Основные HTTP-коды: `400` — параметры, `401` — авторизация, `413` — размер, `422` — повреждённое/неподдерживаемое аудио или превышение длительности, `429` — заняты слоты, `500` — внутренняя ошибка/ошибка очистки, `503` — недоступность ресурсов, `504` — таймаут обработки.

В ответ не попадают внутренние пути, stack trace и полный stderr. В логах — только `request_id`, этап, длительность, размер и код ошибки; без имени исходного файла, текста, аудио и ключей.

### Health check: `GET /healthz`

Единственная служебная ручка, без авторизации. Проверяет только, что приложение живо и способно обслужить HTTP-запрос. Сразу возвращает `200 OK`, `Content-Type: application/json`:

```json
{"status":"ok"}
```

Ответ не зависит от загрузки и прогрева модели, занятости слотов, состояния диска, FFmpeg и очистки файлов. Проверка не запускает модель, не обращается к зависимостям и не занимает слот транскрибации. Ошибки готовности обрабатываются самой ручкой транскрибации.

Если процесс остановлен или HTTP-сервер не отвечает, проверка завершается ошибкой соединения или таймаутом. При штатной остановке ручка отвечает `200`, пока HTTP-сервер ещё принимает запросы. Отдельные `/readyz` и `/metrics` не реализуются.

## 10. Docker-поставка

Поставка: исходники, Dockerfile с несколькими этапами сборки, compose.yaml, пример `.env`, манифест и загрузчик моделей, инструкции подготовки релизных ONNX-комплектов и README с curl-примерами.

Рабочий образ содержит Go-приложение, совместимую `libonnxruntime.so`, FFmpeg, FFprobe, curl для health check, CA-сертификаты для HTTPS-загрузок и необходимые системные библиотеки. Запуск от непривилегированного пользователя. Секреты не встраиваются в образ.

| Путь | Назначение |
|---|---|
| `/models` | Постоянный Docker volume с кэшем моделей, writable для загрузчика |
| `/work` | Временный диск только на время обработки, writable |

В Dockerfile добавить проверку (для порта по умолчанию 8080):

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --start-period=120s --retries=3 \
  CMD curl --fail --silent --show-error http://127.0.0.1:8080/healthz || exit 1
```

При изменении HTTP-порта health check должен использовать тот же порт; Compose должен позволять переопределить проверку и длительность стартового периода. Проверка состояния Docker не должна прерывать активное распознавание. Сам по себе статус `unhealthy` не означает автоматический перезапуск контейнера.

Постоянного пользовательского хранилища и SQLite нет. Постоянно хранятся только модели. На пустом кэше сервис скачивает выбранный комплект; на полном — запускается без сети. Скачивание не зависит от наличия запросов пользователей.

Фрагмент Compose для модели и кэша (авторизация и остальные настройки описываются в полном файле поставки):

```yaml
services:
  asr:
    build: .
    environment:
      GIGAAM_MODEL: ${GIGAAM_MODEL:-gigaam-v3-e2e-rnnt}
      GIGAAM_MODEL_DIR: /models
      GIGAAM_AUTO_DOWNLOAD: "true"
    volumes:
      - gigaam-models:/models

volumes:
  gigaam-models:
```

Пример `.env`:

```dotenv
GIGAAM_MODEL=gigaam-v3-e2e-rnnt
```

Модель можно заменить на `gigaam-v3-e2e-ctc` и выполнить `docker compose up -d`: Compose пересоздаст контейнер при изменении environment. Образ пересобирать не требуется. Удаление volume, например через `docker compose down -v`, удаляет кэш и требует повторного скачивания.

Настройки: выбранная модель, автоскачивание, параметры скачивания, порт, ключ, пути, число одновременных запросов, ONNX threads, ограничения файла/длительности, фазовые таймауты, grace period и резерв свободного места.

## 11. Критерии приёмки

1. Сервис запускается на Linux через Docker с пустым кэшем, автоматически скачивает выбранную модель и VAD и начинает принимать транскрибации. Python на хосте и в рабочем контейнере не требуется.
2. WAV, MP3 и видео возвращают полный текст в одном HTTP-ответе. Видео без аудио возвращает диагностируемую ошибку.
3. Go FP32-инференс каждой из двух поддерживаемых моделей проверен против соответствующего официального FP32-примера: признаки совпадают в установленном численном допуске, транскрипции совпадают. Необъяснённые расхождения блокируют приёмку.
4. Часовая запись обрабатывается синхронно; аудиобуферы и признаки не занимают память пропорционально всей записи. На целевом сервере измерен пик RAM.
5. Проверены тишина, короткие фразы, непрерывная речь и слова на стыках. Нет систематических повторов или пропусков из-за нарезки.
6. JSON и text содержат один и тот же распознанный текст. Поддерживаемый сценарий OpenAI-клиента работает с изменёнными `base_url`, ключом и моделью.
7. До успешного HTTP-ответа каталог запроса отсутствует. На диске нет исходника, WAV, фрагментов или файлов результата.
8. После повреждённого файла, обрыва загрузки, ошибки FFmpeg/ASR, таймаута и отключения клиента временные файлы удаляются после остановки операций; бесконтрольных FFmpeg-процессов нет.
9. Имитированная ошибка удаления блокирует успешный ответ и новые запросы до восстановления. После аварийного завершения остатки удаляются при следующем старте до допуска транскрибаций.
10. При занятом слоте новый запрос получает `429`; при нехватке диска — `503`. Число активных операций не превышает лимит, в том числе во время отмены.
11. Проверены длинный запрос через используемый прокси, обрыв при отправке ответа и завершение контейнера. Сервер не обещает восстановить результат после обрыва.
12. В логах, файлах и кэше нет сохранённого текста/аудио после завершения запроса. Сервис не отправляет их внешним сервисам.
13. Измерены RTF и пик RAM на целевом CPU отдельно для ASR и всего запроса. Указаны CPU, ограничения контейнера, потоки и ревизия модели. Скорость из сторонней статьи не является гарантией; конкретный SLA определяется по этому замеру.

14. `/healthz` возвращает `200` во время загрузки модели, длительной транскрибации и недоступности рабочего каталога, если приложение отвечает по HTTP. При остановленном процессе или неотвечающем HTTP-сервере Docker health check завершается ошибкой. Проверка не требует API-ключа и не запускает модель.

15. После пересоздания контейнера с тем же volume повторного скачивания нет, сервис запускается без сети. Смена `GIGAAM_MODEL` загружает соответствующий комплект; `/v1/models` отражает активную модель, несовпадающий `model` в запросе даёт `400`.
16. Проверены прерванное скачивание, повреждённый файл, нехватка места, отсутствующая сеть и `GIGAAM_AUTO_DOWNLOAD=false`. Частичные модели не загружаются, другая модель не подставляется. `/healthz` остаётся проверкой живого HTTP-приложения.
