# Повторная сборка Alpine

ONNX Runtime собирается отдельно в `Dockerfile.onnx-alpine`. `Dockerfile.alpine` использует локальный результат и не запускает CMake. Это позволяет пересобирать сервис после очистки Docker-кэша без повторной компиляции ONNX.

## Первая подготовка

Из корня репозитория:

```bash
sh scripts/prepare-onnx-alpine.sh > onnx-prepare.log 2>&1
docker compose -f compose.yaml -f compose.alpine.yaml up -d --build
```

Следующую команду запускайте после успешного завершения предыдущей. В другом терминале можно читать `tail -f onnx-prepare.log`. Скрипт выбирает архитектуру Docker-сервера и все доступные ему логические CPU. На HP 6405U это `amd64` и четыре задачи; на Mac учитываются CPU, выделенные Docker VM. При недостатке памяти ограничьте параллелизм: `ORT_BUILD_JOBS=2 sh scripts/prepare-onnx-alpine.sh`. `.env` этот скрипт не читает.

Если Docker требует sudo, используйте `sudo sh scripts/prepare-onnx-alpine.sh`; для явного числа задач — `sudo env ORT_BUILD_JOBS=4 sh scripts/prepare-onnx-alpine.sh`.

Результат — `.onnxruntime/amd64/` или `.onnxruntime/arm64/`: библиотека, лицензии, версия, архитектура, список установленных пакетов сборки и `SHA256SUMS`. При сборке сервиса проверяются контрольные суммы, ожидаемая версия и архитектура. Отсутствующий или повреждённый комплект останавливает сборку. Автоматического перехода к компиляции C++ нет.

Каталог исключён из Git, но включается в Docker build context. Храните его резервную копию отдельно от Docker-кэша. Для другого компьютера той же архитектуры можно перенести каталог целиком с сохранением символических ссылок, например через `tar`. ARM64-библиотека с Mac не подходит HP x86-64. Явная подготовка другой архитектуры: `sh scripts/prepare-onnx-alpine.sh amd64`; для неё Docker должен поддерживать соответствующий builder или эмуляцию.

## Обычная пересборка

Для изменений Go-кода, модели или FP32/INT8:

```bash
docker compose --progress plain -f compose.yaml -f compose.alpine.yaml build > alpine-rebuild.log 2>&1
docker compose -f compose.yaml -f compose.alpine.yaml up -d
```

`build` не меняет работающий контейнер. Запускайте `up -d` только после успешной сборки и завершения текущих запросов. Лог сборки: `tail -f alpine-rebuild.log`; лог сервиса: `docker compose -f compose.yaml -f compose.alpine.yaml logs -f asr`.

На подготовленном HP в `.env` уже есть `COMPOSE_FILE=compose.yaml:compose.alpine.yaml:compose.local.yaml` (последний файл сохраняет [доступ по LAN](hp-lan.md)), поэтому достаточно `sudo docker compose up -d --build`. ONNX заново подготавливать не нужно.

## Осознанное обновление ONNX и инструментов

Базовые Alpine и Go-образы закреплены по digest. Архив ONNX 1.29.0 проверяется SHA-512; CMake-зависимости закреплены самим ONNX в `cmake/deps.txt`. Исправление предупреждения GCC 15 ограничено `logging.cc`: `maybe-uninitialized` остаётся предупреждением, остальные ошибки не отключены.

Для обновления версии ONNX измените URL, SHA-512, версию в метаданных и идентификатор CMake-кэша в `Dockerfile.onnx-alpine`, а также ожидаемую версию в `Dockerfile.alpine` и сообщение скрипта. Новый идентификатор кэша нужен и при смене компилятора/ABI. Базовые digest обновляйте согласованно в обоих Dockerfile и проверяйте совместимость Go-привязки с новой библиотекой. Список установленных ранее пакетов есть в `build-packages.txt`.

Затем повторите подготовку. Скрипт сначала собирает во временный каталог: при ошибке старый комплект остаётся на месте. При успехе предыдущий сохраняется в `.onnxruntime/<архитектура>.previous` (одна копия). Не запускайте две подготовки одной архитектуры одновременно. Пересборку сервиса и проверки выполняйте до переключения рабочего контейнера:

```bash
sh scripts/prepare-onnx-alpine.sh > onnx-prepare.log 2>&1
docker build -f Dockerfile.alpine --target test .
docker compose -f compose.yaml -f compose.alpine.yaml build
```

Перед выкладкой проверьте готовность модели и распознавание контрольного WAV на отдельном экземпляре. Go-тесты сами по себе не подтверждают качество распознавания новой модели или библиотеки.

Это фиксация проверенной ONNX-библиотеки, а не побайтная воспроизводимость всего образа. `apk add` по-прежнему использует обновляемые репозитории выбранной ветки Alpine; FFmpeg, libstdc++ и пакеты сборки Go могут изменяться при новой загрузке слоёв. Чистая подготовка ONNX тоже зависит от этих пакетов и доступности внешних серверов. Digest базового образа не фиксирует содержимое APK-репозитория. Для обычной пересборки прежняя проблема компилятора устранена тем, что компиляции ONNX в ней больше нет.
